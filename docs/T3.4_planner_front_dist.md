# L0 前视距离与 PursuitLocalPlanner 同口径（T3.4）

> 2026-11-24 · 起因：用户给出 B 线默认 `PursuitLocalPlanner` 参数，核对时发现 L0 的固定前视距离与 planner 真实碰撞检测距离差 2.5~4 倍。

## 一、结论先说

L0 之前用**固定** `front_dist`（MapTool 2.0 m / bridge 3.0 m）判"前视命中"。
但 planner 的碰撞检测距离**不是配置里的米数**，而是：

```
检测距离 = collision_linear_vel × max_allowed_time_to_collision
         = 0.4 m/s          × collision_time_*（四场景切换）
```

| 场景 | collision_time | 实际检测距离 | 图上标识 | L0 旧值 | 偏差 |
|---|---|---|---|---|---|
| 直线 | 3.0 s | **1.20 m** | `直` 灰蓝 | 2.00 m | +67% |
| 一般曲线（可绕行） | 2.0 s | **0.80 m** | `弯` 蓝 | 2.00 m | +150% |
| 曲线不绕行 | 2.0 s | **0.80 m** | `弯·不绕行` 紫 | 2.00 m | +150% |
| 曲线掉头 | 1.0 s | **0.40 m** | `掉头` 橙 | 2.00 m | +400% |

旧值在掉头点把检测范围放大 5 倍，是"L0 报擦碰、实车不停"的结构性来源。

### 真实轨迹的四档分布（南岸晶都 `1119主路.json`，4134 点）

| 场景 | 点数 | 占比 | 距离 |
|---|---|---|---|
| 直线 | 3092 | 74.8% | 1.20 m |
| 曲线不绕行 | 857 | 20.7% | 0.80 m |
| **曲线掉头** | **155** | **3.7%** | **0.40 m** |
| 一般曲线 | 30 | 0.7% | 0.80 m |

四档全部命中。这组数字已固化进 `test_planner_limits.cpp::test_real_trajectory_distribution`
作为回归基线——若 `pickScene` 改坏（掉头判不进、`bypass` 反相丢了），测试立刻红。

> ⚠️ 统计口径：`turnAround` 优先于 `bypass`，所以 155 个掉头点是从
> `(curve=1, bypass=1)` 的 1012 点里再切出来的，`no_bypass` 实为 1012−155=857。
> 按属性列分别统计再加总会重复计数。

## 二、源码依据（`pursuit_local_planner.cpp`）

```cpp
// :403  碰撞检测前推速度写死，与 fast_linear_vel 无关
auto collision_linear_vel = 0.4;

// :261-275  四场景切换
if (curve_paths_flag == 1) {
    if (turn_around_flag_ == 1)   max_allowed_time_to_collision_ = collision_time_curve_turn_around_;
    else if (no_bypass_flag_ == 1) max_allowed_time_to_collision_ = collision_time_curve_no_bypass_;
    else                           max_allowed_time_to_collision_ = collision_time_curve_;
} else {
    max_allowed_time_to_collision_ = collision_time_straight_;
}

// :434  沿速度方向逐步前推，直到超时
while (i * projection_time < max_allowed_time_to_collision_) {
    curr_pose.x += projection_time * (collision_linear_vel * cos(curr_pose.theta));
    curr_pose.y += projection_time * (collision_linear_vel * sin(curr_pose.theta));
    ...
}
```

**注意 `collision_linear_vel` 是硬编码常量 0.4**，不是参数。
改 `fast_linear_vel` 不会改变检测距离（实测：容器 `sweeper_v1` 的 `fast_linear_vel=0.5`，检测距离仍按 0.4 算）。

## 三、`bypass` 字段语义是反的

```cpp
// sweep_base.cpp:726
void SweepBase::update_point_counts(int index, int bypass_attr,
                                    std::vector<int>& no_bypass_vector,
                                    std::vector<int>& bypass_vector) {
    if (bypass_attr == 1)      no_bypass_vector.push_back(index);   // ⚠️ 1 → 不绕行
    else if (bypass_attr == 0) bypass_vector.push_back(index);
}

// :757
bool bypass_set    = set_no_bypass_flag(bypass_point_count, false);
bool no_bypass_set = set_no_bypass_flag(no_bypass_point_count, true);
```

**轨迹点写 `bypass: 1` 表示"不允许绕行"**（对应 `no_bypass_flag = 1`）。
标准回归样本 50 个点全是 `bypass: 1`，即全程走「曲线不绕行」档。

`preset` 在 MapTool 里新增参数时按 `bypass` 原名填即可，反相处理只在 `core/planner_limits.cpp` 的 `pickScene()` 里做一次，避免两处语义漂移。

### ⚠️ 直线段上 `bypass` 被忽略（与 planner 一致，非 bug）

planner 源码的判定链是：

```cpp
if (curve_paths_flag == 1) {
    ... 掉头 / 不绕行 / 一般曲线 ...
} else {
    max_allowed_time_to_collision_ = collision_time_straight_;   // bypass 不参与
}
```

即 **`bypass` 只在曲线段内起作用**。南岸晶都真实数据里
`(curve_paths=0, bypass=1)` 有 **2608 点（63%）**，这些点都按直线档 1.20 m 处理。
这不是遗漏，是严格照抄 planner——若真机上直线段也因"不允许绕行"而缩短检测距离，
那是 planner 的另一处行为，需要单独确认后再改。

## 四、实现

### core 层（纯算术，无 Qt/ROS）

`maptool-sim/core/planner_limits.{h,cpp}`

```cpp
struct PlannerLimits {
    double collision_time_straight = 3.0;
    double collision_time_curve = 2.0;
    double collision_time_curve_no_bypass = 2.0;
    double collision_time_curve_turn_around = 1.0;
    double collision_linear_vel = 0.4;
};

struct PointFlags { int curve_paths, turnAround, bypass; };

DriveScene pickScene(const PointFlags&);          // 与源码 if/else 链逐条对齐
double sceneFrontDist(const PlannerLimits&, DriveScene);
double frontDistForPoint(const PlannerLimits&, const PointFlags&);
int parsePlannerLimits(const char* yamlText, PlannerLimits&);  // 不引 yaml 库
```

`parsePlannerLimits` 按行精确匹配 key（`collision_time_curve` 是
`collision_time_curve_no_bypass` 的前缀，必须按完整 key 比对，有专门单测盯着），
缺失项保留默认值而不是归零——归零会让该场景"永不报警"。

### L0 集成

`fov_layer.cpp` 的逐点循环里：

```cpp
blz::PointFlags flags{attr->curve_paths, attr->turnAround, attr->bypass};
double frontDist = m_plannerMode ? blz::frontDistForPoint(m_limits, flags)
                                 : m_front_dist;
if (!(frontDist > 0.0)) frontDist = m_front_dist;   // 兜底，防静默失效
```

`frontDist` 随后同时喂给矩形包络绘制、矩形 raycast（`rp.x_max`）
与扇形 raycast（`fp.front_dist`），三条路径用同一个值，不会出现
"框画 A 大小、判定用 B 距离"。

### 参数来源

mainwindow 启动时按以下顺序找 `local_planner_params.yaml`：

1. `QSettings` 里上次记住的路径（`plannerParamsPath`）
2. 当前工作目录
3. `~/planner/local_planner_params.yaml`

找到就解析覆盖，找不到用内置默认（= 用户给的这份参数），状态栏给提示。
解析成功会把路径记进 `QSettings`，下次直接用。

### UI

前视快算控制面板新增勾选框 **「按轨迹属性分档（弯道/掉头自动切换前视距离）」**：

- **默认勾选**。前视距离本来就该跟随轨迹点属性，这是这个功能的本意。
- 勾上：`前视距离 (m)` 输入框禁用（灰显），下方显示四档实际距离；
  地图上每个检测框按档位配色，并在框旁标 `直` / `弯` / `弯·不绕行` / `掉头`；
  汇总栏追加档位分布，如 `危险点：3 / 4134（最近前视 0.35m）｜直线 3092点(1.20m) · 不绕行 857点(0.80m) · 掉头 155点(0.40m)`
- 取消：回到全程固定值（排查"是不是属性影响导致差异"时用）。

**为什么改成默认开启**：初版做成默认关闭（理由是"不改变既有习惯"），
结果打开前视快算看到的仍是固定 2.0 m、与轨迹属性毫无关系——等于功能没生效。
用户的原始需求就是"依据轨迹点属性自动切换"，默认关闭属于设计错误。

**属性来源**：轨迹 JSON 的 `curve_paths` / `turnAround` / `bypass` 字段，
导入即进 `pt->attr`（`mainwindow.cpp:1037-1073`），界面上 `曲线` 复选框
（`attributeAddDialog.ui` 名为 `curve_paths`，标签「弯道」）可直接标注。

## 六、检测区几何口径（2026-11-24 用户实机截图后修正）

用户在南岸晶都（`1791448885936.pgm` + `1119主路.json`）打开前视快算，
反馈掉头段「按 150 车身都绰绰有余不会发生碰撞」，但界面报 70 个危险点。
查下来是两个独立的几何错误，与档位无关：

### 错误 1：检测区包含了整个车身

```cpp
// 旧代码
const double xMinPx = -(kHalfL + (forcePass ? 0.0 : m_margin)) * invRes;  // 从车尾算起
rp.x_min = -(kHalfL + (forcePass ? 0.0 : m_margin));
```

检测矩形 `x ∈ [-1.175, +2.125]` 覆盖了车尾→车头→前视段。于是**车贴着墙走**
时，车侧与车尾的墙格被算成命中。贴边清扫的正常状态被当成碰撞。

planner 的 `collision_time_*` 只做**前向**预测（沿速度方向前推 `0.4×t` 米），
从不检查车身两侧与后方。修正后：

```cpp
const double xMinPx = kHalfL * invRes;              // 车头前沿起
rp.x_min = kHalfL;
rp.ref_x = kHalfL;                                   // 距离以车头前沿为 0
```

### 错误 2：安全裕度默认 0.25 m 是重复保守

裕度原本对齐 costmap 膨胀半径。但膨胀半径是**给规划器留的余量**，
L0 是"净空排雷"，再算一遍等于同一件事做两次。实测（4134 点全量）：

| 口径 | 命中点数 | 占比 |
|---|---|---|
| 含车身 + 裕度 0.25 | 1017 | 24.6% |
| 仅车头前方 + 裕度 0.25 | 876 | 21.2% |
| **仅车头前方 + 裕度 0** | **108** | **2.6%** |

裕度 0 恰好对应用户的「150 车身绰绰有余」：按真实车宽 1.50 m 判，全轨迹只有
108 个真报警。裕度改为默认 0，需要贴近 costmap 口径时可在面板手动调回 0.25。

### 措辞

`"车身擦碰!"` → `"车头贴障!"`。检测区已不含车身，仍叫"车身擦碰"会让人
误以为真车撞了。

### 回归保护

新增 `core/tests/test_fov_geometry.cpp`（14 断言，`run_smoke.sh` 4.4/8）：

- 空旷场地不报命中
- **车侧贴墙但前方通畅 → 不报命中**（配对照：旧口径 + 裕度 0.25 会命中）
- 车尾后方障碍不参与前视
- 正前方 0.50 m 有墙 → 命中，且距离以车头前沿为 0
- 障碍在检测距离外 → 不命中
- 裕度 0 vs 0.25 的边界行为
- 掉头档 0.40 m 与直线档 1.20 m 对同一堵墙的判定差异（分档确实在起作用）
- `yaw=90°` 旋转后几何仍正确

## 七、跟随项进展与已知限制

1. **bridge 侧直播前视距离已按轨迹点属性分档（2026-11-24 已实现）**
   `live_bridge` 本身仍只推点云与位姿，但 bridge 在宿主机侧持有该 run 的轨迹点
   （请求自带 `traj_json.points`，缺省取场地档案 `bags[].traj` / `default_traj`）。
   `sim-bridge/planner_limits.py` 的 `TrajectorySceneMatcher` 把每帧位姿匹配到轨迹最近点
   （局部窗口 `[last-10, last+40]` 优先、距离 ≤1.5 m 才采信，防往返/交叉轨迹跳段；
   丢失再全局扫描；最近距离 >3 m 视为未匹配，回退固定 `front_dist`），
   用与 C++ 侧完全一致的四档逻辑得到检测距离，`TimelineAdapter` 用它做前视筛选，
   并在 `frame` / `front_hits` 中附带 `scene`、`front_dist`。
   `collision_time_*` 来自 `config/local_planner_params.baseline_20261124.yaml`，
   再叠加 run 的 `param_overrides` / `param_changes`（改参会影响分档距离）。
   未传轨迹点时完全沿用固定值（向后兼容）；`live_bridge` 若将来直推 `point_flags` / `scene`，优先采用。
   ⚠️ 仍是"按位姿匹配最近点"的近似，不是 planner 当前 goal 索引；急转/掉头点附近可能差一两个点。

2. **`lookahead` 理论公式已落地，但不覆盖实测值**
   `use_velocity_scaled_lookahead_dist: true` 时（`:558-576`）：
   ```cpp
   if (robot_vel_.angular.z != 0)  lookahead_dist = 1.5;                    // 有转向 → 死锁 1.5
   else  lookahead_dist = 3/1.5 * speed.linear.x * lookahead_time_;         // 直线 → 2v×3.0
   lookahead_dist = clamp(lookahead_dist, min_lookahead_dist_, max_lookahead_dist_);
   ```
   直线 0.4 m/s → `2 × 0.4 × 3.0 = 2.4 m`，clamp 在 [1.0, 4.0] 内 → **2.4 m**，不是 yaml 里写的 1.5。
   现在 `frame.lookahead_expected` 按此公式给出理论值（角速度优先取上游 `angular_vel`，
   否则由相邻帧 yaw 差估算，阈值 0.02 rad/s）；`frame.lookahead` 仍只放观测节点的实测值
   （未观测就是 `null`，不拿理论值冒充）。报告问题点位卡片显示"实测（理论 x）"，
   lookahead 时间序列下方注明口径。T3.2 校准如需引用 lookahead，请用实测值或 `lookahead_expected`，不要读 yaml。
   注意 `compute_lookahead_dist` 的"有转向"以角速度阈值判断，与 planner 的 `!= 0` 严格判断不同
   （仿真里角速度几乎恒非零，严格判断会让直线也走 1.5），属有意的近似。

3. **`regulated_linear_scaling_min_radius` 差异未处理**
   用户给的 3.0 vs 容器 `sweeper_v1` 的 4.0。该参数只影响弯道降速曲线，
   不进入碰撞检测距离，本次未纳入 `PlannerLimits`。
