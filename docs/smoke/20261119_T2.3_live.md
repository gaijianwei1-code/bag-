# T2.3 WS 实时流（直播跟车）冒烟 — PASS（2026-11-19）

## 核心发现：不重复造轮子
容器里**已有 `live_bridge.py`（294 行）**，已在做 L1 直播要的全部事：
- 5 Hz `state`（位姿/速度/进度，B 线取 `/odom/current_pose` + `/vehicle_cmd` + `/task_progress`）
- 点云抽稀到 ≤220 点并转到 map 系（B 线用当前位姿旋转；A 线走 TF 合成，带 identity map→odom 过滤）
- `path` / `obstacles`（障碍真值）一次性推送
- 输出为 JSON Lines 到 stdout，非 JSON 行（ROS 日志）可安全丢弃

**T2.3 只做三件事**：起它、读它的行、转成我们的 timeline schema。

## 关键设计：前视命中与 L0 同源
`live_adapter.front_hits_from_points()` 用与 `core/fov_raycast` **相同的几何语义**
（锥内 + 距离上限 + 按距离排序 + ≤50 上限）。这样 L1 直播的 `front_hits` 与 L0 预判可比，
T3.2 的一致率校准才有意义。若两边各写一套，校准结果无意义。

## 降频策略
| 源 | 改后 | 理由 |
|---|---|---|
| points 2.5 Hz | 命中 ~0.8 Hz（hit_every=3） | 落在契约 1-2 Hz 区间；语义上命中点变化慢于位姿 |
| state 5 Hz | frame 5 Hz | 契约 5-10 Hz |
| progress（百分比） | status.progress（0-1） | 契约归一化 |

## 过程修正（测试假设错误，非产品 bug）
初版写了「无回放时也应收到 hello」的 docker 用例 → 实测失败：`live_bridge` 的
`rospy.init_node` 要连 ROS master，无回放时 master 不存在，脚本按设计重试 60 次后
`emit({"type":"status","state":"error","reason":"no ROS master"})` 退出。
**这是正确行为**。测试改为：
1. `test_live_stream_reports_no_master`：无 master → 必须优雅报 error（不崩溃、不静默）
2. `test_live_stream_with_real_replay`：端到端起回放 → 须收到 hello + ≥10 帧
并把 docker 类用例设为默认跳过（`addopts = -m "not docker"`），避免每次冒烟等 90 s。

## 接线
`app.py::_execute_run` 现在会：
1. 先起 `LiveStream`（它自己等 ROS master）
2. 再调 `runner.submit()` 起闭环回放
3. 直播 `frame` 直接 append 进 `run["frames"]`；`front_hits` 挂到最近一帧（契约：随帧捎带）
4. `path`/`obstacles` 存 run 级字段
5. 结束时停流并留 `live_stderr_tail`（排错用）

WS 侧仍按 T0.1 契约轮询 `frames` 增量发送 → **断线重连天然补齐**（数据在服务端，不在流里）。
