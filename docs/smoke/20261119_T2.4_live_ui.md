## 冒烟抓出的真 bug
`FAIL: run_id 为空应报 error 而非静默`
根因：`m_state` 只在 dock 的 `stateChanged` 回调里赋值 → **没有 dock 时状态读不到**。
修复：所有 `emit stateChanged(...)` 之前先给 `m_state` 赋值（6 处）。
这是"状态机状态依赖 UI 存在"的设计缺陷，不是测试问题。

### 联调抓出的真 bug（adapter 空参数）
```
FileNotFoundError: [Errno 2] No such file or directory: ''
```
`b_line_run.py` 第 6 个参数是 adapter 路径，传空字符串会直接 `open('')` 报错，
**不像第 5 个参数那样能省略**。
根因：我加 `ps_dir`（第 5 参数）时保留了末尾的 `''`，于是 adapter 变成了真正的空参数。
修复：命令改为 `... {cpath} {ps_dir}`（省略 adapter，用默认值）。

**UI 表现**：run 在 0 秒变 failed，用户点「连接」会看到"什么都没发生"，无法排查。
这就是端到端联调的价值——单测和冒烟都不会碰这条路径。

### 遗留问题
**metrics 全为 None**：`_record_to_metrics()` 的名字映射与 run_record 实际结构不匹配。
run_record 有 `schema/line/run_id/started_at/ended_at/duration_s/scene/param_set/param_plan/...`，
但 F 门指标（tracking_rms 等）不在顶层，需要进一步定位实际字段路径。

## metrics 映射修复（2026-11-19 10:02）
**根因**：指标数据不在 `run_record.json`（那只是输入配置记录），而在 **`summary.json`**：
```
motion:       {travel_m, path_length_m, end_error_m, progress_peak, progress_100}
edge_lateral: {count, rms, max, mean_signed, p95_abs}
commands:     {count, nonzero, mean_speed, max_speed}
task:         {goal_reached_count, result_status_counts}
obstacles:    {status, reason}
```
**修复**：`runner._read_record` → `_read_summary`（改读 summary.json）；
`app._record_to_metrics` 按真实结构重写，并新增 **`moved` 判定**：
```python
moved = (travel_m > 0.1)
gates = "未达标：车未移动（虚拟雷达判满障碍）" if not moved else "已移动，指标待完整评估"
```
这一条直接把 W16 的虚拟雷达问题暴露在 UI 上，不用翻日志。

**MapTool 侧显示**：`行程 x/y m  偏差RMS z  命令 n/m`

**实测该样本的 metrics**：
```
travel_m 0.0 / path_length_m 25.63 / end_error_m 25.18
cmd_count 259 / cmd_nonzero 0 / mean_speed 0.0
moved: False → "未达标：车未移动"
```
与项目总览 W16 记录的「2791 条速度指令全为 0、车原地不动」一致。

## 可用性问题修复（2026-11-19 10:30）— 用户实测反馈

**用户遇到的实际问题**：按指引跑完 `e2e_ui_check.py` 拿到 run_id，但
①bridge 进程已退出，内存数据全丢 ② 即使 bridge 在，run 已完成 → WS 只推一次，MapTool 连上看到空白。

### 修复 1：WS 支持已完成 run 的时间轴回放
`app.run_stream` 增加分支：若 `state in (done, failed)` 且有缓冲帧，
按**原始 t 字段 pace 到 1x 速度**推送（0.25s 前瞻批次），推完再发 metrics + status。
**实测：184 帧 / 31.8s → PASS**（不再是瞬间刷完）。

### 修复 2：`demo_live.sh` 一键演示
起 bridge（常驻）→ 跑一次 run → 等完成 → 打印 run_id + MapTool 操作指引 → **保持运行**。

### 修复 3（真 bug）：档案 bag 名与 venue_id 命名不一致
```
档案里:  bags/scenario_1793346971223.bag   （下划线）
调用方:  bags/scenario-1793346971223.bag   （连字符，与 venue_id 一致）
→ bag_in_venue() 返回 False → 422「bag 未在场地档案登记」
```
已统一为连字符。**这个 bug 之前没暴露，是因为 e2e_ui_check.py 恰好用了档案里的原名**——
换个调用方（demo 脚本、C 客户端）就撞上。

### 教训
验收一个"用户能操作"的功能，必须按**用户实际的使用顺序**走一遍：
起服务 → 提交任务 → **等服务完成** → 再连 UI。
我之前的联调是"提交后立刻连 WS"，正好避开了这个坑。
