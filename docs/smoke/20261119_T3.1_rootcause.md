# T3.1 lookahead 根因确认 + 第二层阻塞（2026-11-19）

## 第一层：已解决 —— tolerance 6 m 导致 planner 不参与控制
```
next_goal_tolerance_normal: 6 m  → lookahead/plan/theta 全空（planner 未进 CONTROLLING）
next_goal_tolerance_normal: 1 m  → lookahead ✓  received_global_plan ✓  vehicle_cmd ✓
```
**机制**：`schedule_goal.yaml` 的 `loop_rate: 0.1`（10 Hz 定时器）驱动 `loopSendGoal`；
`next_goal_tolerance_normal=6 m` 在 **25.7 m 长、50 个点**的短轨迹上意味着几乎每个点都"在容差内"，
于是每 0.1 s 发一个新 goal 并取消前一个 → `sweep_base::executeCb` 反复被打断 →
`runPlanner_` 设 true 后立即被覆盖 → `executeCycle` 的 `while(!runPlanner_)` 得不到完整周期 →
`PursuitLocalPlanner::computeVelocityCommands()` 从未执行。

**参数与场景尺度必须匹配**：6 m 容差是为实车大场地设的，短轨迹上必须调小。
历史先例 `w1_tolerance_0.3`（6→0.3）得到"96% 停车、无终态"——说明 0.3 又太小（车到不了那么准）。
**1.0 m 是当前 bag 的可用工作点。**

## 第二层：仍阻塞 —— 车不动（不是 planner 的问题）
调 tolerance 后：
```
sweep_base/status: status 1 "goal accepted"    ✓（goal 正常了）
vehicle_cmd:       speed 0.0, mode 0           ✗（主动停车）
位姿位移:          0.0 m                        ✗
```
**根因**：`sweep_base.cpp` 里 `isTargetPoseValid(goal.pose)` 返回 false →
`publishZeroVelocity()` + `ros::Duration(5.0).sleep()` →
`ROS_ERROR("Encountering obstacles has already begun to wait......")`
即**目标点被判为"被障碍物占用"**。这正是项目总览记录的未解决缺陷：
> 新场地虚拟雷达把整片区域判为障碍（`Found a safe angular velocity` 20,344 次、速度指令 2791 条全为 0、车原地不动）
